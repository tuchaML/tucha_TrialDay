Вот **прямые ответы на все семь вопросов задания №2**, без лишней теории. Именно их нужно отразить в `SOLUTION.md`.

### **1. В каком поле предлагается включить индекс и какой строкой Odoo это делает?**

В файле `addons/tucha_crm/models/request.py`, в модели `tucha.request`, предлагаю включить индекс для поля `planned_from`.

**Было:**

```
planned_from = fields.Datetime(string="Окно с", required=True)
```

**Предлагается:**

```
planned_from = fields.Datetime(    string="Окно с",    required=True,    index=True,)
```

Параметр `index=True` позволяет Odoo создать стандартный B-tree индекс PostgreSQL.

**Почему:** поле используется для диапазонного поиска по датам, тогда как `active` и `stage` уже индексированы.

### **2. Какой отдельный метод модели&#x20;**`tucha.request`**&#x20;будет собирать условия поиска?**

Предлагаю создать метод `_get_open_requests_domain()` в `request.py`.

```
@api.modeldef _get_open_requests_domain(self, date_from, date_to):    return [        ("active", "=", True),        ("stage", "not in", ("completed", "cancelled")),        ("planned_from", ">=", date_from),        ("planned_from", "<", date_to),    ]
```

**Почему:** сейчас правила отбора открытых заявок определяются внутри `dashboard.py`. Если они понадобятся другим отчётам, разработчики могут начать дублировать код.

Новый метод станет единым местом формирования условий поиска.

### **3. Какие параметры метод принимает и что возвращает?**

Метод принимает:

- `date_from` — начало периода включительно.
- `date_to` — конец периода исключительно.

Возвращает `domain`**&#x20;— список условий поиска Odoo**.

Метод не обращается к PostgreSQL и не возвращает сами заявки. Он только формирует фильтр, который затем используется для поиска.

### **4. Как&#x20;**`dashboard.py`**&#x20;будет использовать этот метод?**

Вместо самостоятельного формирования условий дашборд вызовет новый метод.

**Было:**

```
domain = [    ("active", "=", True),    ("stage", "not in", ("completed", "cancelled")),    ("planned_from", ">=", start),    ("planned_from", "<", end),]
```

**Станет:**

```
request_model = self.env["tucha.request"]domain = request_model._get_open_requests_domain(    date_from=start,    date_to=end,)
```

Дальнейшие операции останутся без изменений:

```
count = request_model.search_count(domain)requests = request_model.search(    domain,    order="planned_from, id",    limit=8,)
```

Таким образом, `request.py` определяет **какие заявки искать**, а `dashboard.py` — **какие показатели рассчитывать и отображать**.

### **5. Какие два теста предлагается добавить?**

**Тест №1 — правильность условий поиска.**

Создать заявки с разными статусами, активностью и датами. Проверить, что:

- `new` и `processing` включаются;
- `completed` и `cancelled` исключаются;
- неактивные заявки исключаются;
- заявка ровно в начале периода включается;
- заявка ровно в конце периода исключается.

Тест должен выполнить реальный `search(domain)` и проверить найденные записи.

**Тест №2 — наличие индекса.**

Проверить, что после обновления модуля:

- у поля `planned_from` установлен параметр `index=True`;
- в PostgreSQL действительно существует соответствующий B-tree индекс таблицы `tucha_request`.

Для проверки физического индекса можно использовать системные каталоги PostgreSQL.

### **6. Что необходимо проверить при обновлении существующей базы?**

Перед внедрением:

1. Создать резервную копию базы.
2. Проверить существующие индексы и объём таблицы.
3. Проверить актуальность статистики PostgreSQL; при необходимости выполнить `ANALYZE`.
4. Обновить модуль Odoo, чтобы индекс появился физически.
5. Убедиться, что существующие заявки и даты не изменились.
6. Запустить тесты и сравнить результаты поиска до и после.
7. Проверить планы запросов через `EXPLAIN (ANALYZE, BUFFERS)` на репрезентативной базе.

Отдельно нужно оценить возможные блокировки при создании индекса на большой таблице.

### **7. Какие риски или недостатки есть у решения?**

**Основной риск:** добавление индекса не гарантирует ускорение.

PostgreSQL выбирает план запроса самостоятельно, учитывая статистику и количество подходящих записей.

Дополнительные ограничения:

- Индекс занимает место и увеличивает затраты на запись.
- Запрос фильтрует сразу три поля. Возможно, составной или частичный индекс окажется эффективнее.
- Перенос `domain` в отдельный метод улучшает поддержку кода, но сам по себе не ускоряет поиск.
- При добавлении новых статусов необходимо пересмотреть правило определения открытой заявки.
- На большой рабочей базе создание индекса может сопровождаться блокировками.

**Итоговое решение:** начать с обычного индекса по `planned_from` и выделения общего метода формирования `domain`. После внедрения проверить фактическую производительность и при необходимости пересмотреть стратегию индексирования.
